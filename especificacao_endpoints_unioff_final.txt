ESPECIFICACAO DOS ENDPOINTS - UNIOFF
=====================================

1. INFORMACOES GERAIS
=====================

URL base:
/api

Formato padrao:
Content-Type: application/json

Autenticacao:
Os endpoints protegidos devem receber o JWT no cabecalho:
Authorization: Bearer <token_jwt>

Perfis:
- ESTUDANTE
- EMPRESA
- ADMIN

Tabelas:
- USUARIO
- ESTUDANTE
- EMPRESA
- BENEFICIO
- RESGATE

Regras gerais:
- USUARIO.email deve ser unico.
- ESTUDANTE.usuario_id deve ser unico.
- EMPRESA.usuario_id deve ser unico.
- RESGATE.codigo_cupom deve ser unico.
- Senhas devem ser armazenadas como hash BCrypt em senha_hash.
- O hash da senha nunca deve ser retornado pela API.
- IDs do estudante e da empresa autenticada devem ser obtidos pelo JWT.
- Datas usam o formato ISO 8601, exemplo: 2026-09-01.
- Data e hora usam o formato: 2026-09-01T14:30:00.
- BENEFICIO.quantidade_resgates inicia em 0.
- BENEFICIO.quantidade_max_resgastes deve ser maior que 0.
- Um resgate so pode ser criado quando quantidade_resgates for menor que quantidade_max_resgastes.
- A exclusao de beneficios deve ser logica, alterando ativo para false.

Codigos HTTP:
- 200 OK: operacao realizada com sucesso.
- 201 Created: recurso criado com sucesso.
- 204 No Content: operacao realizada sem corpo de resposta.
- 400 Bad Request: dados invalidos.
- 401 Unauthorized: token ausente, expirado ou invalido.
- 403 Forbidden: usuario sem permissao.
- 404 Not Found: recurso nao encontrado.
- 409 Conflict: conflito com recurso existente ou cupom ja utilizado.
- 422 Unprocessable Entity: regra de negocio nao atendida.

Formato padrao de erro:
{
  "status": 422,
  "error": "Unprocessable Entity",
  "message": "O limite maximo de resgates foi atingido.",
  "path": "/api/beneficios/10/resgates",
  "timestamp": "2026-09-01T14:30:00"
}


2. MODELO DAS TABELAS
=====================

TABELA: USUARIO

Descricao:
Armazena os dados de autenticacao e identificacao dos usuarios.

Campos:
- id (PK)
- nome (not null)
- email (not null, unique)
- senha_hash (not null)
- tipo_usuario (ESTUDANTE, EMPRESA, ADMIN) (not null)
- ativo (not null, default true)
- data_criacao

Relacionamentos:
- 1:1 com ESTUDANTE
- 1:1 com EMPRESA

--------------------------------------------------

TABELA: ESTUDANTE

Descricao:
Armazena informacoes especificas dos estudantes.

Campos:
- id (PK)
- usuario_id (FK -> usuario.id, not null, unique)
- instituicao (not null)
- curso
- matricula (opcional)

Relacionamentos:
- 1:1 com USUARIO
- 1:N com RESGATE
- N:N com BENEFICIO atraves de RESGATE

--------------------------------------------------

TABELA: EMPRESA

Descricao:
Armazena os dados dos estabelecimentos cadastrados.

Campos:
- id (PK)
- usuario_id (FK -> usuario.id, not null, unique)
- nome_fantasia (not null)
- descricao
- cidade (not null)
- bairro (not null)
- logradouro (not null)
- numero (not null)
- telephone_whatsapp
- site

Relacionamentos:
- 1:1 com USUARIO
- 1:N com BENEFICIO

--------------------------------------------------

TABELA: BENEFICIO

Descricao:
Armazena os beneficios disponibilizados pelas empresas.

Campos:
- id (PK)
- empresa_id (FK -> empresa.id, not null)
- titulo (not null)
- descricao
- data_inicio
- data_fim
- quantidade_resgates (not null, default 0)
- quantidade_max_resgastes (not null)
- ativo (not null, default true)

Relacionamentos:
- N:1 com EMPRESA
- 1:N com RESGATE

Restricoes recomendadas:
- quantidade_resgates >= 0
- quantidade_max_resgastes > 0
- quantidade_resgates <= quantidade_max_resgastes
- data_fim >= data_inicio, quando ambas forem informadas

Campos calculados retornados pela API:
- quantidadeDisponivel = quantidadeMaxResgastes - quantidadeResgates
- esgotado = quantidadeResgates >= quantidadeMaxResgastes

Os campos quantidadeDisponivel e esgotado nao precisam existir no banco.

--------------------------------------------------

TABELA: RESGATE

Descricao:
Armazena os resgates realizados pelos estudantes.

Campos:
- id (PK)
- estudante_id (FK -> estudante.id, not null)
- beneficio_id (FK -> beneficio.id, not null)
- codigo_cupom (not null, unique)
- data_resgate
- utilizado (not null, default false)

Relacionamentos:
- N:1 com ESTUDANTE
- N:1 com BENEFICIO


3. CADASTRO E AUTENTICACAO
==========================

3.1 CADASTRAR ESTUDANTE
-----------------------

Historia:
COMO ESTUDANTE,
QUERO criar uma conta na plataforma,
PARA acessar os beneficios oferecidos pelas empresas parceiras.

Endpoint:
POST /api/auth/estudantes

Acesso:
Publico.

Dados enviados:
{
  "nome": "Marcos Aurelio Santos",
  "email": "marcos@email.com",
  "senha": "Senha@123",
  "instituicao": "Universidade Exemplo",
  "curso": "Engenharia de Software",
  "matricula": "20260001"
}

Processamento:
1. Validar os dados.
2. Verificar se o email ja existe.
3. Criar USUARIO com tipoUsuario ESTUDANTE e ativo true.
4. Gerar senha_hash com BCrypt.
5. Criar ESTUDANTE associado ao USUARIO.
6. Salvar as duas entidades na mesma transacao.

Resposta - 201 Created:
{
  "id": 1,
  "usuarioId": 1,
  "nome": "Marcos Aurelio Santos",
  "email": "marcos@email.com",
  "instituicao": "Universidade Exemplo",
  "curso": "Engenharia de Software",
  "matricula": "20260001",
  "tipoUsuario": "ESTUDANTE",
  "ativo": true,
  "dataCriacao": "2026-09-01T14:30:00"
}

Erros:
- 400: dados invalidos.
- 409: email ja cadastrado.

6. RESGATES E CUPONS
====================

6.1 RESGATAR BENEFICIO
----------------------

Historia:
COMO ESTUDANTE,
QUERO resgatar um beneficio,
PARA utiliza-lo em um estabelecimento parceiro.

Endpoint:
POST /api/beneficios/{beneficioId}/resgates

Acesso:
Autenticado como ESTUDANTE.

Dados enviados:
Nenhum corpo JSON. O estudante e identificado pelo JWT.

Processamento obrigatorio:
1. Identificar o ESTUDANTE pelo JWT.
2. Localizar o BENEFICIO.
3. Verificar se o beneficio esta ativo.
4. Verificar data_inicio e data_fim.
5. Verificar se quantidade_resgates < quantidade_max_resgastes.
6. Impedir concorrencia na ultima vaga por bloqueio ou atualizacao atomica.
7. Gerar codigo_cupom unico.
8. Criar RESGATE com utilizado false.
9. Definir data_resgate.
10. Incrementar quantidade_resgates em 1.
11. Salvar RESGATE e incremento na mesma transacao.

Resposta - 201 Created:
{
  "id": 100,
  "codigoCupom": "UNI-A8KX91",
  "dataResgate": "2026-09-01T15:00:00",
  "utilizado": false,
  "beneficio": {
    "id": 10,
    "titulo": "20% de desconto em pizzas",
    "quantidadeResgates": 26,
    "quantidadeMaxResgastes": 100,
    "quantidadeDisponivel": 74,
    "esgotado": false
  },
  "empresa": {
    "id": 1,
    "nomeFantasia": "Pizzaria Universitaria"
  }
}

Resposta quando esgotado - 422:
{
  "status": 422,
  "error": "Unprocessable Entity",
  "message": "O limite maximo de resgates deste beneficio foi atingido."
}

Erros:
- 403: usuario nao possui perfil ESTUDANTE.
- 404: beneficio nao encontrado.
- 409: estudante ja resgatou, caso exista limite por estudante.
- 422: beneficio inativo, fora da vigencia ou esgotado.

9. CONTROLE DE CONCORRENCIA NOS RESGATES
========================================



Problema: ( Não nos preocupemos com isso agora)
Dois estudantes podem tentar resgatar a ultima vaga ao mesmo tempo.

Regra obrigatoria:
A verificacao do limite, a criacao do RESGATE e o incremento de quantidade_resgates devem ocorrer na mesma transacao.

Opcoes de implementacao:
- Bloqueio pessimista do registro BENEFICIO.
- Controle otimista com campo de versao.
- Atualizacao condicional atomica.

Regra equivalente da atualizacao atomica:
Incrementar quantidade_resgates somente quando:
quantidade_resgates < quantidade_max_resgastes

Se nenhuma linha for atualizada:
- nao criar o RESGATE;
- desfazer a transacao;
- retornar 422 informando que o beneficio esta esgotado.

Invariante do sistema:
quantidade_resgates nunca pode ser maior que quantidade_max_resgastes.
